# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

ROS 2 **Humble** autonomous-driving stack for a small Ackermann-steered inspection vehicle, running on an NVIDIA Orin (`nvidia` user). The repo is a colcon workspace: source packages live under `src/`, with `build/`, `install/`, and `log/` produced by colcon. The vehicle talks to its chassis over **SocketCAN (`can0`)**. Most code comments and launch descriptions are in Chinese.

The workspace root also holds many loose operational artifacts that are *not* part of the build: map files (`map*.pcd/pgm/yaml`), rosbag recordings (`bag*/`, `rosbag2_*`, `mapping_bag_*`), and standalone helper scripts (`run_route.py`, `odom_to_tf.py`, `upload_map.py`, etc.). These are run ad-hoc with `python3`, not via the package system.

## Build & Run

```bash
# Build everything (run from workspace root /home/nvidia/auto_driving)
colcon build --symlink-install
# Build a single package
colcon build --symlink-install --packages-select <pkg_name>
# Always source after building (every new shell)
source install/setup.bash

# Run a node / launch
ros2 run <pkg> <executable>
ros2 launch <pkg> <file>.launch.{py,xml}
```

There is no test/lint harness wired up beyond the default `ament` test stubs autogenerated in Python packages (`test/test_flake8.py`, etc.). Run them with `colcon test --packages-select <pkg>` if needed, but they are boilerplate, not real coverage.

## Architecture: the runtime pipeline

The stack is the classic sense → localize → perceive → plan → control → actuate chain, wired together over ROS topics. Key end-to-end data flow:

- **Sensing** (`src/driver/`): `lidar` (RoboSense via `rslidar_sdk` → `/rslidar_points`), `imu`, and `camera`/`camera_driver_all` (multi-cam publisher → `camera_front/image_raw` etc.). `pointcloud_to_laserscan` converts `/rslidar_points` → `/scan` for 2D obstacle logic.
- **Localization** (`src/localization/lidar_localization_ros2`): NDT-based lidar localization against a prebuilt `.pcd` map. Subscribes to point cloud + IMU + odom + initialpose, publishes `PoseWithCovarianceStamped`, a `car_msg/OrinPose`, and a path. Other localization dirs (`funny_lidar_slam`, `lidarslam_ros2`, `lightning-lm`, `rtabmap_ros`) are alternative/experimental SLAM backends used for **mapping**, not the live localization path.
- **Perception** (`src/perception/yolov5_ros2`): YOLOv5 2D detector (`yolo_detect_2d.py`), subscribes `image_raw` topics, runs on `cuda:0`.
- **Planning** (`src/planning/`): `emplanner` (C++ EM-planner + hybrid-A\*, subscribes current/end pose + occupancy grid, publishes `/planned_path`), `costmap_generator` (grid_map/PCL based), `laser_avoid` (subscribes `/scan`, publishes `std_msgs/Bool` on an obstacle topic), and `navigation_ros2` (Nav2 action-based goal handling).
- **Control** (`src/control/car_simple_follow`): `simple_follow` pure-pursuit-style follower. Subscribes `/vehicle_info`, the avoidance `Bool`, and `nav_msgs/Path` trajectory; publishes `car_msg/VehicleState` on **`/control_cmd`**.
- **Vehicle interface** (`src/vehicle/car_cmd_interface`): the CAN bridge. Subscribes `/cmd_vel` (Twist), `/angle` (Float32), and `/control_cmd` (`VehicleState`); does Ackermann steering conversion; writes CAN frames to `can0`; publishes chassis feedback on **`/vehicle_info`**. This is the only node that touches hardware CAN — a `cmd_timeout` (default 0.25 s) stops the car if commands stall.

So two parallel control entry points exist: Nav2 drives `/cmd_vel`, while `car_simple_follow` drives `/control_cmd`. Both funnel into `car_cmd_interface`.

## Custom messages

`src/msg/car_msg` defines the shared interface types — **most packages depend on `car_msg`**:
- `VehicleState.msg`: velocity, steering, brake, gears, led, battary — the universal command/feedback type.
- `OrinPose.msg`: a stamped `geometry_msgs/Pose`, published by localization.

When changing these `.msg` files, rebuild `car_msg` first, then every dependent package.

## Launch orchestration

Two launch styles coexist:
- `src/launch` (package `orin_launch`): the intended modular entry point. `orin.launch.xml` toggles modules (`launch_sensing`, `launch_localization`, `launch_perception`, `launch_planning`, `launch_control`, `launch_vehicle`) and includes per-module xml under `launch/<module>/`. **Note:** several of these included files are currently empty stubs or reference paths that don't exist yet (`step1_*.launch.xml`, `map/`), so this tree is partially wired.
- `allin.launch.py` (in `src/launch/launch`): a concrete, working bring-up that sequences lidar → laserscan → localization → `nav2_map_server` (with manual lifecycle configure/activate via `TimerAction`) → `car_cmd_interface`, using hardcoded absolute paths.
- `src/control/car_simple_follow/launch/start_all.launch.xml`: bring-up for the follow-the-path control demo (localization + laser_avoid + simple_follow).

When wiring new bring-up, prefer extending the modular `orin_launch` xml tree, but check `allin.launch.py` and `start_all.launch.xml` for the actually-tested node sequences and parameter values.

## Gotchas

- **Hardcoded absolute paths**: launch files and scripts contain machine-specific paths like `/home/nvidia/ros2_ws/maps/map.yaml` (note: *different* from this workspace's own `maps/`) and `/home/nvidia/auto_driving/...`. Verify the path actually points where you intend before relying on it.
- **Map files are large and numerous** (`map.pcd` ~48 MB, `map11.pcd` ~140 MB). The "active" map is generally `map.pcd`/`map.pgm`/`map.yaml` at the root; the numbered variants are historical captures.
- **Lifecycle nodes**: `nav2_map_server` and the lidar localization component are managed-lifecycle nodes — they need explicit `configure`/`activate` transitions (see the `ros2 lifecycle set` calls in `allin.launch.py`).
- Mixed package types: C++ uses `ament_cmake` (CMakeLists.txt), Python uses `ament_python` (setup.py). Check the package's `package.xml` `<build_type>` before adding files.
